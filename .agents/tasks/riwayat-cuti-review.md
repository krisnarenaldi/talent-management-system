# Riwayat Cuti (Leave History) tab on employee detail page

This change adds a "Riwayat Cuti" tab to `/employees/[id]`, following the exact same add/view/delete pattern as the existing Kontrak tab. A new `EmployeeLeave` model and migration back the feature, three REST endpoints (`GET /POST /DELETE`) hang off `/{employee_id}/leaves`, and the frontend wires it up through a `LeavesTab` component with a form card, a table-based list, and `react-query` mutation hooks. The implementation deliberately mirrors ContractsTab — same dependency injection, same toast pattern, same empty/loading states.

Watch for: **(confirmed)** list layout diverges from ContractsTab (table vs card-per-row); submit button is always enabled instead of disabled when fields are empty; pre-existing `extracted_json` TEXT→JSONB schema drift will cause noisy autogenerate stubs on the next migration. None are blocking.

**Verdict**: APPROVED

---

## High-level view

The backend model `EmployeeLeave` is structurally identical to `EmployeeContract`: UUID PK with `default=uuid.uuid4`, CASCADE FK to `employee.id`, and `server_default=func.now()` on `created_at`. The `leaves` relationship on `Employee` uses the same `cascade="all, delete-orphan"` as every other child relationship. The Pydantic schemas follow the Base → Create → Response pattern with `from_attributes = True`, and `EmployeeLeaveCreate` correctly exposes only the three user-facing fields (`start_date`, `end_date`, `reason`).

The three router endpoints match the contracts section closely. GET and POST carry dual-decorator registration (with and without trailing slash); DELETE has a single route, consistent with how `delete_contract` is registered. The `_raise_404` helper is reused identically for 404 responses. Write endpoints are protected by `require_role("hr", "manager", "admin")`; the read endpoint uses `get_current_user` — matching the contracts access model exactly.

The frontend `LeavesTab` uses `useQuery` + two `useMutation` hooks with `queryClient.invalidateQueries` on success, matching `ContractsTab`. Client-side validation toasts an error if any of the three fields is empty before firing the mutation, which is a small UX improvement over ContractsTab's silent disabled-button approach. The list renders as a table (not card-per-row like ContractsTab) — functionally equivalent and arguably better for a multi-column dataset, but it's a deliberate deviation from the plan spec.

The Alembic migration situation is noted in the plan: the autogenerated migration picked up pre-existing schema debt (`extracted_json` TEXT→JSONB cast), so the coder stubbed that revision and created a clean separate migration for `employee_leaves` only. Both migrations ran successfully and the table exists. This is a pragmatic resolution to a pre-existing schema drift problem, not a new concern introduced by this PR.

<summary>Details</summary>

### Submit button always enabled

`ContractsTab` disables the submit button when fields are missing (silent UX). `LeavesTab` instead calls `showToast("error", ...)` before aborting — the button is always enabled and empty-field feedback comes as a toast rather than a disabled state. Strictly better feedback, but inconsistent with the contracts pattern. Decide on one approach for the codebase.

### No start_date ≤ end_date validation

The backend accepts any `start_date`/`end_date` combination without checking that start precedes end. A record with `end_date < start_date` will be stored and displayed. Given the scope ("bukan untuk log cuti"), this is a deliberate trade-off — one `@model_validator` in the Pydantic schema fixes it if needed.

### Pre-existing schema drift not resolved

The stub migration (`10e7822c0983`) exists to bypass an autogenerate false-positive on the pre-existing `extracted_json` TEXT→JSONB column mismatch. The `employee_leaves` table is created correctly by the chained migration (`v1w2x3y4z5a6`). The underlying mismatch is still present, so the next `alembic revision --autogenerate` will regenerate the same noisy stub unless cleaned up in a separate migration.
